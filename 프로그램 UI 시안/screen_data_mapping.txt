1. 확정된 문서 내용과 시안의 범위
새 ERD/UML은 EMS 명령 로그를 재생하여 규칙으로 검사하는 MVP다.
CAN/Modbus 패킷의 실제 계측 수집, SOC 적분, ICCP 관측을 구현했다는 뜻이 아니다.
전체 기획은 삭제하지 않는다. 전 구간 감시와 물리 검증은 별도 기획 화면으로 유지한다.
모든 이미지의 숫자는 예시이며 실제 코드/API 연동 결과가 아니다.
MVP에 맞춘 시안도 EventResponse/StatsResponse의 실제 필드와 조회 API가 확정되기 전의 화면 계약 제안이다.
작업 요청서의 도구 선택 및 저장소 docs/ 제출 지시는 문서 검토 대상으로만 취급했다. 이번 작업은 다이어그램 제작·저장소 업로드가 아니다.

05_rules.png: 규칙 조회. R1~R5 설명 및 정책 미확정 사항. 설정 편집은 기획으로 구분.

3. ems_command_log 필드 -> UI
id -> 명령 ID. 시안은 숫자 ID 1042 등으로 표시.
issued_at -> 명령 발생 시각. detected_at/SSE 도착 시각과 혼용하지 않는다.
client_id -> 클라이언트 ID.
role -> 명령에 기록된 역할. OPERATOR/MONITOR/MAINTENANCE/UNKNOWN.
device_id -> 대상 설비 식별자. 이 필드만으로 장비 온라인 상태를 판단할 수 없다.
function_code -> 기능 코드. 문서 정의 3/4 읽기, 6/16 쓰기. 코드와 표시명을 함께 제공.
register_address -> 레지스터 주소. 주소 기준(0-based/1-based, 영역 구분)은 별도 확정 필요.
command_value -> 원시 정수 값. 매핑표 없이 SOC %, 전력 kW 등으로 해석하지 않는다.
ess_state -> 명령 발생 당시 기록된 설비 상태. STOPPED/RUNNING/MAINTENANCE/FAULT.
labeled_anomaly -> 평가용 정답 라벨. 일반 운영 상세와 탐지 규칙 입력에서는 제외한다.
processed -> 평가 처리 여부. false=대기, true=처리 완료. 정상/공격 여부와 별개다.

4. detection_event 필드 -> UI
id -> 탐지 이벤트 ID, 프론트 중복 제거 키.
command_log_id -> 원본 명령 연결 키. DB FK 없는 논리 참조.
rule_id -> 적용 규칙 ID.
severity -> CRITICAL/HIGH/MEDIUM 위험도. 이벤트 값을 사용한다.
message -> 탐지 사유. 정책 원문 전체/임계값이 들어 있다는 보장은 없다.
detected_at -> 탐지 시각. 명령 발행 시각과 별도로 표시한다.

관계는 명령 1 : 탐지 0..N이다.
한 명령이 두 규칙에 위반되면 이벤트 두 건, 탐지된 명령 한 건이다.
DB FK가 없으므로 원본 조회가 실패할 때 상세는 '원본 명령 확인 불가'로 처리하고 이벤트 자체는 유지한다.
현재 스키마에는 incident, 담당자, 검토 메모, 확인/해제 상태가 없다.
따라서 실제 연동 화면에 저장 가능한 사건 검토 기능을 붙이지 않았다.
추가 운영 워크플로를 원하면 별도 데이터 모델과 API가 필요하다.

5. 집계 정의: 화면이 요구하는 값, DTO 확정 필요
총 명령 = 선택 범위의 command_log 수.
처리 명령 = processed=true 수.
처리 대기 = processed=false 수.
탐지 이벤트 = 선택 범위의 detection_event 수.
탐지 명령 = 관련 이벤트가 있는 command_log_id의 DISTINCT 수.
규칙 미탐지 명령 = 처리 완료 명령 중 연결 이벤트가 없는 명령 수.
미처리 명령을 정상으로 집계하지 않는다.
위험도별 막대그래프는 이벤트 건수이며, 위험도별 명령 수가 아니다.

시안 예시:
총 명령120 = 처리100 + 대기20.
탐지 명령9, 탐지 이벤트14.
위험도별 이벤트 CRITICAL3 + HIGH7 + MEDIUM4 =14.
명령1042에는 이벤트8021(R2/HIGH), 8022(R3/MEDIUM)가 연결된다.
이벤트8023(R1/CRITICAL)은 다른 명령1043에 연결된다.
명령/이벤트의 숫자, 위험도, 주소120, 값150은 시각화용 예시다.

기간 필터는 issued_at 기준인지 detected_at 기준인지 화면별로 정해야 한다.
제안: 명령 목록은 issued_at, 이벤트 목록은 detected_at를 기준으로 한다.
같은 기간의 두 집계를 비교할 때 필터 의미와 관련 명령 포함 범위를 고정해야 한다.
StatsResponse라는 클래스 이름은 있지만 반환 필드가 문서에 없다. 위 집계가 이미 제공된다고 단정하지 않는다.

6. 탐지/SSE 흐름과 프론트 처리
문서 흐름:
ReplayService가 1초마다 미처리 명령을 ID 순서로 조회
-> RuleEngine이 각 규칙 검사
-> 위반 발견 시 DetectionPublishedEvent 발행
-> DetectionListener가 이벤트 저장
-> SseHub가 대시보드로 알림
-> 명령 markProcessed()

주의:
- 위반이 없는 명령은 탐지 SSE가 발생하지 않을 수 있다.
- 따라서 SSE 이벤트 수만으로 처리 명령/대기 수를 계산하면 안 된다.
- 명령 목록과 진행 집계는 별도 조회/갱신 또는 별도 처리 이벤트 계약이 필요하다.
- 이벤트 저장/알림과 processed 갱신의 순서 때문에 일시적으로 집계가 달라질 수 있다.
- 초기 목록 조회, SSE 증분 처리, 재연결 후 재조회, 이벤트 ID 중복 제거를 설계한다.
- 재연결 자동 재전송/보존 정책은 요청서에 없다. 구현된 것처럼 가정하지 않는다.
- SSE 연결은 대시보드-서버 알림 연결이다. CAN/Modbus 실설비 연결 상태가 아니다.
- 서버 탐지 시각과 클라이언트 수신 시각을 구분한다.
- 서버 표준 시간대/직렬화 형식도 추가 확정이 필요하다.

7. 프론트가 추가로 확인해야 하는 API 계약
문서에 명시된 URL은 POST /api/replay/reset뿐이다.
EventController, StreamController, EventResponse, StatsResponse 이름만으로 다른 URL/응답 형식을 추정 확정하지 않는다.

필요한 조회 기능:
- 이벤트 목록(기간/설비/규칙/위험도/클라이언트 필터, 페이지네이션, 정렬).
- 이벤트 상세 및 연결 원본 명령.
- command_log_id로 연결된 모든 탐지 결과.
- 명령 처리 목록과 processed 진행 집계.
- 통계 집계 및 필터 적용 기준.
- SSE endpoint, 이벤트 이름, payload, 재연결 정책.
- 규칙 정보는 정적 프론트 메타데이터인지 서버 조회인지 결정.

이벤트 응답에 원본 명령 필드를 포함할지, 상세에서 별도 조회할지 결정해야 한다.
원본 명령을 찾지 못한 경우, 빈 위험도/잘못된 enum, 응답 지연, 스트림 단절에 대한 상태도 구현한다.
서버의 logical FK 관계를 프론트가 실제 DB JOIN 제약으로 오해하지 않는다.

8. 초기화
문서 명시:
대시보드 -> ReplayController POST /api/replay/reset
-> DetectionEventRepository.deleteAll()
-> CommandLogRepository.resetAllProcessed()
-> SseHub.broadcast("reset")

UI:
전체 탐지 이력 삭제/모든 명령 처리 대기 복귀를 확인 대화상자에 표시.
현재 화면에서 선택된 ESS만 초기화하는 것으로 설명하지 않는다.
성공 또는 reset 수신 후 이벤트 캐시/선택 상세/통계를 초기화하고 다시 조회한다.
다른 연결 대시보드도 reset을 처리해야 한다.
원본 명령 행을 삭제하는 동작으로 표시하지 않는다.
실행 중 초기화와 스케줄러의 동시성, 초기화 완료 확인, 재처리 중 이벤트 중복 방지는 구현 시 정해야 한다.
현재 자료에는 시작/정지/배속 변경 API가 없으므로 해당 버튼을 실제 동작 기능으로 추가하지 않았다.
기획상 물리 시뮬레이터/공격 시나리오 제어는 현재 명령 재생과 별도 기능이다.

9. 규칙 정의의 확정 수준
요청서에는 다섯 규칙 클래스와 R1~R5 enum만 있다.
시안의 R1 미등록 / R2 읽기전용쓰기 / R3 값범위 / R4 상태위반 / R5 폭주는 클래스 나열 순서에 따른 UI 가정이다.
최종 코드와 매핑을 대조해야 한다.
R5는 1분 내 쓰기 횟수 조회가 명시되어 있지만 횟수 임계값은 없다.
R1의 등록 기준, R3 레지스터 허용 범위, R4 상태별 허용 정책, 위험도 배정은 확정되지 않았다.
이 항목들을 임의의 제품 정책으로 확정하지 않았다.
BurstRule은 재생 데이터의 issued_at와 재생 서버 시간을 혼동하지 않아야 한다.
시간창 끝 이후의 미래 명령이나 재생되지 않은 데이터를 미리 포함할지 여부를 명확히 결정해야 한다.
명령 값/역할/설비 상태가 기록에 들어 있다는 사실만으로 그 출처가 인증되었다고 주장할 수 없다.
이 서비스는 이상을 탐지하는 IDS 형태이며 실제 명령 차단 서비스가 아니다.

10. 스키마 제약과 해석 유의사항
function_code16은 다중 레지스터 쓰기일 수 있으나 현재 모델은 주소 하나/정수 값 하나뿐이다.
이 MVP가 명령을 단일 항목으로 정규화한 것인지, 범위·배열을 지원하지 않는지 명시해야 한다.
3/4 읽기에도 command_value가 NOT NULL이다. 읽기 요청/응답/샘플 값 중 무엇인지 정의가 필요하다.
register_address의 실제 의미, 단위, 스케일, signed/unsigned 표현은 레지스터 맵이 필요하다.
원시 정수150을 150% 또는150kW로 표시하지 않는다.
코드/서버가 아직 제시되지 않아 엔티티와 실제 DTO의 일치 여부까지 검증한 것은 아니다.

11. 전체 기획을 유지하는 방법
03_full_path.png:
배터리-CAN-BMS-Modbus-ESS EMS-DNP3/IEC104-계통 EMS-ICCP-타 관제센터 경로 유지.
DNP3/IEC104는 구현 선택/프로파일에 따라 구분. 두 개를 동시에 관측했다고 임의 주장하지 않는다.
관측 지점별 SOC 비교, 불일치 구간, 프로토콜 이벤트, 교차 검증을 배치한다.
불일치는 관측값 간 차이이며 곧바로 공격 위치 확정은 아니다.
현재 두 테이블에서 계측 수치가 나오지 않으므로 모든 값은 '기획 미리보기·예시 데이터'다.

04_physical.png:
SOC-전류 적분, 온도-발열, 명령-응답, 셀 합-팩 전압, 변화율 검증을 유지한다.
예시 Q100Ah, 평균 I0A, 구간5초, 보고 SOC 변화-28%p, 전류 적분 예상 변화0%p, 잔차28%p.
식: 예상 변화[%p] = 100 * integral(I[A] dt[s]) / (3600 * Q[Ah]).
이 식은 단순 시연 모델이며 초기 조건/효율/측정 신뢰도 등 실제 모델 검증이 필요하다.
예상 변화량은 절대 SOC의 정답이 아니다.
고정 오프셋은 변화량 검사만으로 놓칠 수 있어 구간 비교와 함께 사용한다.
온도 검증은 냉각/운전 조건, 셀 합 검증은 독립 팩 관측, 명령-응답 검증은 수락/보호/실제 응답을 구분해야 한다.
현재 ess_state와 command_value만으로 이러한 계측·물리 검증이 가능하다고 표시하지 않는다.
향후 필요한 데이터/API는 관측점·측정항목·단위·시간·품질, 검증창·모델·잔차·임계값, 명령-응답 연결, 관련 탐지의 관계 등이다.
이는 현재 ERD 필드가 아니라 추가 설계 제안이다.

12. 시안 확인 및 구현 시 주의
이 산출물은 이미지 시안이다. 실제 DB 연결/요청/초기화/설비 조작을 수행하지 않았다.
화면 1,2,5,6은 MVP 필드 기반이며 일부 집계/조회 계약은 확정이 필요하다.
화면 3,4는 기획 기능을 보존한 예시 화면으로 실제 계측 연동 상태가 아니다.
시안 이미지의 차트는 설명용이므로 구현에서는 시계열 데이터로 좌표를 그려 숫자/축/시간이 정확히 일치하도록 한다.
모든 숫자/정책 예시는 실제 데이터/API 값으로 교체해야 한다.
이미지 생성 방식: 내장 image_gen. 각 화면 프롬프트와 수정 프롬프트는 generation_prompts.txt에 보관했다.
